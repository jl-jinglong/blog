上一篇[上下文扩展的位置与训练方法](/posts/long-context/)讲的是"**怎么让模型看懂更长的输入**"——位置怎么编码、注意力看多远、训练怎么安排。但那篇笔记刻意绕开了一类问题：**就算方法都对，这套东西在显存和带宽上跑得动吗？**

这两件事必须分开看。一个模型可以完美支持 128K 的语义理解，却在单卡上跑不起来；反过来，一个推理框架可以靠各种技巧把 1M token 塞进显存，模型却完全抓不住中间的信息。

这篇笔记集中讲**工程侧**：显存怎么花、缓存怎么管、计算怎么分布到多张卡上。全篇围绕一句话展开：

> **长上下文推理的成本不是一个数，而是两个——prefill 和 decode。它们卡在不同的地方，要用不同的手段解。**

## 1. 先分清 prefill 和 decode

自回归生成分成两个阶段，它们的瓶颈完全不同：

| 阶段 | 做什么 | 计算特征 | 主要瓶颈 |
| --- | --- | --- | --- |
| **Prefill** | 一次性处理整段输入，建立 KV cache | 可以并行，是**大矩阵乘法** | 算力（$N^2$ 的注意力计算） |
| **Decode** | 逐 token 生成，每次只算一个新 token | 串行，每步都要读全部历史 KV | **内存带宽**（KV cache 的读取量） |

**为什么这个区分重要？** 因为优化的手段完全不同。

- Prefill 慢，是因为注意力要算 $N\times N$ 的相关性矩阵，计算量随长度**平方**增长。要加速就得减少计算量——用稀疏注意力、或者换更高效的内核。
- Decode 慢，是因为每生成一个 token，都要把**全部历史**的 KV 从显存里读一遍。计算量其实很小（就一个 token 的矩阵向量乘），但显存读取量随长度**线性**增长。这时候 GPU 的算力根本用不满，全在等数据搬运。

> 一个常见的误判：看到"长上下文推理很慢"就以为要换更快的卡。如果瓶颈在 decode 的带宽上，换卡提升有限；如果瓶颈在 prefill 的算力上，才轮得到算力优化。**先测清楚是哪个阶段慢，再决定优化什么。**

## 2. KV cache：长上下文显存的主要去处

### 2.1 为什么需要缓存

自回归生成时，第 $t$ 个 token 的注意力需要前面所有 token 的 K 和 V。如果不缓存，每生成一个新 token 都要把整段历史重新算一遍 K、V，计算量会变成 $O(N^3)$。

所以推理框架会把算过的 K、V 存下来，这就是 **KV cache**。缓存之后，每步只需要为新 token 算一份 K、V，复杂度回到 $O(N^2)$。

### 2.2 缓存有多大

KV cache 的大小可以这样估：

$$
\text{bytes}=2\times L\times n_{\text{layer}}\times n_{\text{kv\_head}}\times d_h\times \text{precision}.
$$

- $2$：K 和 V 各一份。
- $L$：序列长度（token 数）。
- $n_{\text{layer}}$：层数。
- $n_{\text{kv\_head}}$：KV 头数量（用了 GQA 之后比 Q 头少很多）。
- $d_h$：每个头的维度。
- $\text{precision}$：每个数占的字节数，FP16 是 2。

**关键点是 $L$ 在分子上**：序列翻倍，缓存就翻倍。上下文从 4K 到 128K，缓存涨了 32 倍。而且它和 batch size 相乘，所以并发请求一多，显存会被 KV cache 吃掉大头。

这也解释了两件事：

- **为什么 GQA / MQA 这么重要**：减少 $n_{\text{kv\_head}}$ 能直接按比例缩小缓存；
- **为什么量化 KV cache 有效**：把 $\text{precision}$ 从 2 降到 1，缓存直接减半。

### 2.3 缓存和位置扩展的冲突

KV cache 和某些位置方法之间有个容易忽略的坑。

RoPE 的做法是**在算注意力之前**对 Q、K 施加旋转。如果缓存的是**旋转后**的 K，那么一旦位置缩放规则变了（比如 Dynamic NTK 随长度调整了频率），缓存里的 K 就对应着旧频率，和新的 Q 对不上。

解决办法有两个：缓存**旋转前**的 K，每次用时再旋转；或者在规则变化时同步更新整个缓存。这也是 Dynamic NTK 在工程上比看起来麻烦的原因。

## 3. 记忆与流式输入

如果输入是连续不断的（对话流、日志流），不可能无限保留全部 KV。这一节讲三种"少存一点"的思路。

### 3.1 Transformer-XL：跨段复用

Transformer-XL 把长文本切成 segment，并把**前一段的隐藏状态**作为下一段的记忆来用，这样信息可以跨段传递，不必在每段重新开始。

它还配合相对位置编码，让记忆跨段时不受绝对位置编号的影响。

**代价**：记忆通常会被截断，而且反向传播一般不会穿过记忆（否则和完整长序列训练没区别）。所以信息不是无损保留的。

### 3.2 StreamingLLM：保留 attention sinks 和最近窗口

流式解码最直觉的做法是只保留最近 $W$ 个 token 的 KV，把旧的扔掉。但实验发现这么做**会崩**：困惑度会突然飙升。

作者找到的原因是 **attention sinks**——模型会把大量注意力分配给**最前面的少数几个 token**，即使这些 token 在语义上毫无价值（比如一个句号、一个起始符）。原因和 softmax 的归一化性质有关：模型需要一个"什么都不关注"的落点来安放多余的注意力权重。一旦把这个落点删掉，softmax 被迫把权重重新分配到其他 token 上，分布就乱了。

StreamingLLM 因此保留**两部分**：

```text
最前面的若干 sink token  +  最近的 W 个 token
```

这样缓存大小是固定的（不随输入增长），却能在很长的流上稳定运行，而且**不需要重新训练模型**。

> **但要说清楚它不是什么**：StreamingLLM 不是"无限上下文理解"。被丢弃的中间历史**无法再被访问**，模型只是能稳定地继续生成。它适合连续对话、实时日志这类"只需要近期上下文"的场景，不适合需要回溯整篇文档的任务。

### 3.3 Infini-attention：把历史压成固定状态

Infini-attention 在同一个 Transformer block 里同时维护两条通路：一条是**局部因果注意力**（看最近的 token），另一条是**压缩长期记忆**（一个固定大小的状态）。

新 token 到来时，历史信息被更新进那个固定大小的记忆状态里。于是显存不再随序列长度增长，而是**有界的**。

**关键取舍**：内存有界了，但被压缩的历史**无法再按原 token 精确恢复**。它更像一个可学习的摘要器，而不是完整 KV cache——适合"记住大意"的任务，不适合"逐字检索原文"。

## 4. 系统优化：让它在硬件上跑得动

前面几节在"少存一点"上做文章，这一节讲**不改变数学结果**的前提下，怎么让计算跑得更快。

### 4.1 FlashAttention：不改变注意力定义，只改怎么算

标准注意力实现会把 $N\times N$ 的注意力矩阵**显式写出来**再和 V 相乘。这个矩阵在长序列下非常大，而且要反复在显存（HBM）和计算单元之间搬运。

FlashAttention 用 **tiling（分块）** 把注意力拆成小块，在片上高速缓存（SRAM）里算完再写回，避免显式保存完整的 $N\times N$ 矩阵。它的核心收益是**减少 HBM 读写**。

必须强调：

> FlashAttention **不改变注意力的数学定义**——算出来的结果是精确的，不是近似。它降低的是系统成本，不改变 RoPE 的训练范围，也不提升模型的语义理解能力。

### 4.2 Ring Attention：把序列切到多张卡

单卡放不下超长序列时，Ring Attention 把序列切成 block 分到多张卡上：每张卡负责自己的 query block，同时在一个设备环里**轮换 KV block**，让每张卡都能看到完整的 KV。

通信和计算可以重叠，所以多卡能共同承载更长的序列。它保持完整注意力的数学结果，解决的是单卡显存和分布式问题。

同样要注意：如果模型没有做过长位置训练或外推，**Ring Attention 不会自动带来长上下文理解**。它只是让你能跑。

### 4.3 MInference 与 chunked prefill：专治 prefill

长上下文推理的瓶颈**往往先出现在 prefill**。两个常见手段：

- **MInference**：观察不同 attention head 的注意力模式（比如 A-shape、Vertical-Slash、Block-Sparse），为每个 head 离线挑一个合适的稀疏 pattern，推理时只算选中的位置。因为它是**按 head 定制**的，比全局用一个固定稀疏模式更贴合实际分布。
- **Chunked prefill**：把超长输入拆成若干块，分多次送进模型。它不减少总计算量，但能让调度更平滑，避免一次塞满显存。

这两个都是**推理加速**，不是位置外推。Qwen2.5-1M 的报告里同时用了 DCA/YaRN（管语义长度）和稀疏 prefill（管系统效率），两者解决的是不同层次的问题，不要混为一谈。

## 5. 怎么判断一个方法真的有效

工程上最贵的错误，是把"能跑"当成"能用"。这一节给几个检查点。

### 5.1 不要只看"最大长度"

至少要同时报告：

- 预训练长度和长上下文微调长度分别是多少；
- 推理时用了什么 RoPE scaling、DCA 或稀疏 attention 配置；
- prefill 延迟、decode 吞吐和 KV cache 占了多少显存；
- 扩展到长上下文后，**原来的短上下文能力有没有回退**。

最后一条经常被忽略：为了让模型支持 128K，如果牺牲了 4K 内的表现，那可能是笔亏本买卖。

### 5.2 困惑度只是第一关

长文本 PPL 能看出模型有没有整体退化，但**不能证明它找得到关键信息**。常见的测试：

- **Passkey / Needle-in-a-Haystack**：把一条信息埋在长文本里，看能不能检索出来；
- **RULER**：组合检索、聚合、长距离依赖和多步任务；
- **LongBench**：长文档问答、摘要、代码和多语言任务；
- **Long-context QA / multi-hop**：需要跨多个位置组合证据。

> 只在开头或结尾插一个 passkey，很容易**高估**模型的真实长文档能力。还要测中间位置、多个干扰项、以及需要跨段推理的任务。

### 5.3 最容易踩的坑

1. **只改 `max_position_embeddings`**：这只改变允许的索引范围，不会自动修复 RoPE 外推；
2. **训练和推理的 RoPE 参数不一致**：`rope_theta`、scaling factor、原始上下文长度必须对应上；
3. **把训练长度和外推长度混写**：32K 训练、128K 推理和 1M 配置不是同一个承诺；
4. **忽略 KV cache**：prefill 能跑通，不代表 decode 能在显存里维持全部历史；
5. **把 FlashAttention / Ring Attention 当成语义扩展**：它们只改善系统可运行性；
6. **只测 PPL 或单一 NIAH**：有效性必须用多种任务交叉验证；
7. **过度依赖 sliding window**：窗口降低成本，但可能切断需要直接访问的远距离证据。

## 6. 结语：两个层次，别混着谈

回到开头那句话——长上下文不是一项技术，而是**两层不同的问题**：

```text
语义层（上一篇文章）：
  位置怎么编码 → PI / NTK / YaRN / LongRoPE / DCA
  注意力看多远 → Window / Sparse / Dilated
  怎么训练     → 课程式长训 / PoSE / LongLoRA

工程层（本文）：
  显存怎么省   → KV cache 量化 / GQA / StreamingLLM / Infini-attention
  计算怎么快   → FlashAttention / MInference / chunked prefill
  怎么扩展到多卡 → Ring Attention
```

最重要的区分是：

> **位置方法和训练方法决定模型"懂不懂"长上下文；缓存和系统优化决定这件事"跑不跑得动"。前者不行，后者再好也没用；后者不行，前者再好也上不了线。**
